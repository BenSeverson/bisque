# RB-1: MAX31856 Driver Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the MAX31855 thermocouple driver with a MAX31856 one, so a rev B board can read temperature.

**Architecture:** `components/thermocouple/` keeps its current public API shape (`thermocouple_init`, `thermocouple_read`, `thermocouple_get_latest`, `temp_read_task`) so no caller changes. Internally the read becomes a register-addressed SPI transaction instead of a single 32-bit frame, with a config-register write on init and a fault-register decode. Channel awareness is deliberately **not** in this plan — that is RB-3.

**Tech Stack:** ESP-IDF `driver/spi_master.h`, Unity host tests, MAX31856 datasheet.

**Issue:** [#306](https://github.com/BenSeverson/bisque/issues/306)

**Spec:** [`docs/firmware-backlog.md`](../../firmware-backlog.md) RB-1

## Global Constraints

- **Register constants in this plan are written from datasheet knowledge, not from a datasheet in hand. Verify every value in Task 1 against the real MAX31856 datasheet before flashing anything.** A wrong register write is a silent miscalibration, not a build error. The verification step is Task 1 and it is not optional.
- The public API in `thermocouple.h` must not change in this plan. `firing_engine`, `safety` and `tests/host/stubs/thermocouple_host.c` all consume it; widening it is RB-3.
- `thermocouple_reading_t` keeps its existing fields. `internal_temp_c` is the cold junction on both parts, so it carries over.
- After editing any firmware C/H file, run `clang-format -i` on it.
- Commit messages end with `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.
- This is bring-up code that cannot be tested on hardware until a board exists. Everything that *can* be host-tested — register encoding, temperature conversion, fault decode — **must** be, because the bench session is the only other place these bugs surface.

Both worked examples in Task 2's tests reproduce the datasheet's own tables
exactly: Table 3 gives +25.00 °C as `0000 0001 1001 0000 0000 0000` (0x019000)
and −1.00 °C as `1111 1111 1111 0000 0000 0000` (0xFFF000); Table 2 gives
+25 °C as `0001 1001 0000 0000` (0x1900).

**Correction 1 — `MAX31856_CR0_OCFAULT1` is misnamed. The value is right; the name is not.**
CR0 bits [5:4] are `OCFAULT[1:0]`, so **bit 4 is OCFAULT0** and bit 5 is
OCFAULT1 (p. 18). `0x10` therefore sets `OCFAULT[1:0] = 01`, which is the
setting this board wants — Table 4, p. 14: *enabled, once every 16 conversions,
`R_S` < 5 kΩ*. The rev B front end is 100 Ω series with 100 nF differential
(`REV-B-NOTES.md` §5c), so `R_S` ≈ 100 Ω and τ ≈ 10 µs, far inside both
thresholds. Rename the macro; do not change the value.

**Correction 2 — `MASK` does not gate what this driver reads.** p. 21: "Masked
faults **will still result in fault bits being set** in the Fault Status
register (0Fh)." MASK gates only the `~FAULT` **output pin**, which rev B does
not route to a GPIO. The write is kept (it costs one transaction and makes
`~FAULT` usable at a test point) but the plan's comment "Unmask every fault we
decode" overstated it — the polled decode is unaffected either way.

**Correction 3 — the CR0 write must be split in two.** p. 19, on the 50/60 Hz
bit: "Change the notch frequency only while in the 'Normally Off' mode – not in
the Automatic Conversion mode." A single write that sets CMODE and the filter
bit together changes the notch on the same edge that starts conversions. This
happens to be harmless at 60 Hz (the bit is 0 both before and after, since
factory-default CR0 is 0x00), but it is wrong by construction for anyone who
later selects 50 Hz. Write CR0 **twice**: once with CMODE clear to establish the
notch and open-circuit settings, then again with CMODE set to start converting.
One extra 2-byte transaction at boot.

**Facts found that the plan did not carry, and that the code should encode:**

- **Comparator mode is what makes polling work.** CR0 bit 2 `FAULT` = 0 selects
  comparator mode (p. 19), in which "the fault status bits simply reflect the
  state of any faults… deasserting when the fault condition is no longer true"
  (p. 25). Interrupt mode would latch until a `FAULTCLR` write. `CR0_INIT` leaves
  bit 2 clear, so no fault-clear path is needed — but that is load-bearing, not
  incidental.
- **CR0 bit 3 `CJ` must stay 0** to keep the internal cold-junction sensor
  enabled (p. 19). Setting it turns 0Ah/0Bh into registers an external sensor
  writes, and `internal_temp_c` would report whatever was last written.
- **Open-circuit detection is not instantaneous.** `OCFAULT[1:0] = 01` tests
  "once every 16 conversions" (p. 19) ≈ every 1.6 s in auto mode. A severed
  thermocouple is detected within ~2 s, not on the next read.
- **OVUV suspends conversions while present** (pp. 14, 26), so an out-of-rail
  input freezes the temperature rather than reporting a plausible one — the safe
  direction, and the reason mapping OVUV to a real fault bit matters.
- **The four threshold faults cannot fire unless we arm them.** Factory defaults
  put them at the extremes — CJHF 7Fh (+127 °C), CJLF C0h (−64 °C), LTHFTH/LTHFTL
  7Fh/FFh, LTLFTH/LTLFTL 80h/00h (Table 6, p. 18). Leaving `TCHIGH`/`TCLOW`/
  `CJHIGH`/`CJLOW` out of the decode is therefore safe, not a gap.
- **SR bits 7 and 6 (`CJ Range`, `TC Range`) are deliberately not decoded.**
  `TC Range` asserts outside K-type's −200…+1372 °C and the reported temperature
  is *clamped* at the limit (p. 15), so an out-of-range hot junction surfaces as
  a 1372 °C reading that `safety`'s over-temp cutoff already catches. Mapping it
  would mean a new `TC_FAULT_*` bit, which is exactly the contract change
  Task 2's OVUV note argues against.
- **Timing leaves the 250 ms poll intact.** Auto-mode conversions 2..n take 82 ms
  typ / 90 ms max at 60 Hz (p. 4); 4-sample averaging adds
  `(4−1) × 16.67 ms` (p. 20), for ~132 ms typ / ~140 ms max. Every 250 ms poll
  therefore gets a fresh conversion, so `temp_read_task`'s period does not change.

    TEST_ASSERT_FLOAT_WITHIN(0.01f, -1.0f, max31856_decode_tc(raw));

static void test_decode_tc_resolution_is_one_128th(void)
{

/* components/thermocouple/max31856_regs.h */
#pragma once

#include <stdint.h>

/* Register addresses. Write = address | 0x80. */
#define MAX31856_REG_CR0   0x00
#define MAX31856_REG_CR1   0x01
#define MAX31856_REG_MASK  0x02
#define MAX31856_REG_CJTH  0x0A
#define MAX31856_REG_LTCBH 0x0C
#define MAX31856_REG_SR    0x0F
#define MAX31856_WRITE_BIT 0x80

/* CR0: continuous conversion, 60 Hz rejection, open-circuit detection on.
   OCFAULT[1:0] live in bits 5:4, so 0x10 is OCFAULT0 — mode 01, "every 16
   conversions, R_S < 5 kOhm", which is this board's 100 Ohm front end. */
#define MAX31856_CR0_CMODE     0x80
#define MAX31856_CR0_OCFAULT0  0x10
#define MAX31856_CR0_FILT_50HZ 0x01
/* Everything except CMODE — written first, so the notch is settled before
   conversions start (the datasheet forbids changing it in auto mode). */
#define MAX31856_CR0_SETUP (MAX31856_CR0_OCFAULT0)
#define MAX31856_CR0_INIT  (MAX31856_CR0_SETUP | MAX31856_CR0_CMODE)

/* CR1: 4-sample averaging, K-type. */
#define MAX31856_CR1_AVG4   0x20
#define MAX31856_CR1_TYPE_K 0x03
#define MAX31856_CR1_INIT   (MAX31856_CR1_AVG4 | MAX31856_CR1_TYPE_K)

/* MASK gates only the ~FAULT pin, never the SR bits this driver polls
   (datasheet p. 21). Written anyway so ~FAULT is live at its test point. */
#define MAX31856_MASK_INIT 0x00

/* SR fault bits */
#define MAX31856_SR_OPEN  0x01
#define MAX31856_SR_OVUV  0x02
#define MAX31856_SR_TCLOW 0x04
#define MAX31856_SR_TCHIGH 0x08

#include "thermocouple.h" /* for TC_FAULT_* */

/* Linearized TC temperature: 19-bit signed in bits [23:5], LSB 2^-7 C. */
static inline float max31856_decode_tc(const uint8_t raw[3])
{
    int32_t v = ((int32_t)raw[0] << 16) | ((int32_t)raw[1] << 8) | raw[2];
    v >>= 5;                     /* right-justify the 19 bits */
    if (v & 0x40000) {           /* sign-extend from bit 18 */
        v |= ~0x3FFFF;
    }
    return (float)v / 128.0f;
}

/* Cold junction: 14-bit signed in bits [15:2], LSB 2^-6 C. */
static inline float max31856_decode_cj(const uint8_t raw[2])
{
    int16_t v = (int16_t)(((uint16_t)raw[0] << 8) | raw[1]);
    v >>= 2;
    return (float)v / 64.0f;
}

/* Map SR to the TC_FAULT_* bits the rest of the firmware already handles.
   The MAX31855 distinguished short-to-GND from short-to-VCC; the MAX31856
   does not, so OVUV — an input outside the rails, the same physical failure
   class — is reported as TC_FAULT_SHORT_GND rather than invented as a new
   bit. Adding a bit would mean a contract change in api_json.c and both
   schemas for no diagnostic gain. */
static inline uint8_t max31856_decode_faults(uint8_t sr)
{
    uint8_t f = 0;
    if (sr & MAX31856_SR_OPEN) {
        f |= TC_FAULT_OPEN_CIRCUIT;
    }
    if (sr & MAX31856_SR_OVUV) {
        f |= TC_FAULT_SHORT_GND;
    }
    return f;
}
```

static esp_err_t reg_write(uint8_t reg, uint8_t val)
{
    uint8_t tx[2] = {reg | MAX31856_WRITE_BIT, val};
    spi_transaction_t txn = {.length = 16, .tx_buffer = tx};
    return spi_device_transmit(s_spi_dev, &txn);
}

static esp_err_t reg_read(uint8_t reg, uint8_t *out, size_t n)
{
    uint8_t tx[5] = {reg};
    uint8_t rx[5] = {0};
    if (n > sizeof(tx) - 1) {
        return ESP_ERR_INVALID_SIZE;
    }
    spi_transaction_t txn = {
        .length = 8 * (n + 1),
        .tx_buffer = tx,
        .rx_buffer = rx,
    };
    esp_err_t ret = spi_device_transmit(s_spi_dev, &txn);
    if (ret == ESP_OK) {
        memcpy(out, rx + 1, n); /* first byte is the address phase echo */
    }
    return ret;
}
```

- [ ] **Step 3: Write the config registers in `thermocouple_init`**

After `spi_bus_add_device` succeeds, and **before** the "initialized" log line:

Note the CR0 write is split (Task 1, correction 3): the notch-filter and
open-circuit bits are established with CMODE clear, and only then does a second
write start continuous conversion.

```c
    esp_err_t cfg = reg_write(MAX31856_REG_CR0, MAX31856_CR0_SETUP);
    if (cfg == ESP_OK) {
        cfg = reg_write(MAX31856_REG_CR1, MAX31856_CR1_INIT);
    }
    if (cfg == ESP_OK) {
        cfg = reg_write(MAX31856_REG_MASK, MAX31856_MASK_INIT);
    }
    if (cfg == ESP_OK) {
        cfg = reg_write(MAX31856_REG_CR0, MAX31856_CR0_INIT);
    }
    if (cfg != ESP_OK) {
        ESP_LOGE(TAG, "MAX31856 config write failed: %s", esp_err_to_name(cfg));
        return cfg;
    }

    /* Read CR0 back. An absent or miswired part clocks back 0x00 or 0xFF
       rather than what we just wrote, and a driver that cannot tell those
       apart reports 0 C forever — which firing_engine treats as a fault only
       after APP_TEMP_FAULT_TIMEOUT_MS, with the element on the whole time. */
    uint8_t cr0 = 0;
    if (reg_read(MAX31856_REG_CR0, &cr0, 1) != ESP_OK || cr0 != MAX31856_CR0_INIT) {
        ESP_LOGE(TAG, "MAX31856 not responding: CR0 read back 0x%02x, expected 0x%02x",
                 cr0, MAX31856_CR0_INIT);
        return ESP_ERR_NOT_FOUND;
    }

    ESP_LOGI(TAG, "MAX31856 initialized on CS pin %d", cs_pin);
```

- [ ] **Step 4: Replace `thermocouple_read`**

```c
esp_err_t thermocouple_read(thermocouple_reading_t *out)
{
    uint8_t sr = 0, cj[2] = {0}, tc[3] = {0};

    esp_err_t ret = reg_read(MAX31856_REG_SR, &sr, 1);
    if (ret == ESP_OK) {
        ret = reg_read(MAX31856_REG_CJTH, cj, sizeof(cj));
    }
    if (ret == ESP_OK) {
        ret = reg_read(MAX31856_REG_LTCBH, tc, sizeof(tc));
    }
    if (ret != ESP_OK) {
        ESP_LOGE(TAG, "SPI read failed: %s", esp_err_to_name(ret));
        return ret;
    }

    out->timestamp_us = esp_timer_get_time();
    out->fault = max31856_decode_faults(sr);

    if (out->fault != 0) {
        out->temperature_c = 0.0f;
        out->internal_temp_c = 0.0f;
        ESP_LOGW(TAG, "Thermocouple fault: SR=0x%02x -> 0x%02x", sr, out->fault);
        return ESP_OK;
    }

    out->temperature_c = max31856_decode_tc(tc);
    out->internal_temp_c = max31856_decode_cj(cj);
    return ESP_OK;
}
```

Note the fault path zeroes the temperature exactly as the MAX31855 driver did — `firing_engine.c` has a comment relying on that behaviour, so changing it here would break a documented assumption.
